# パイプライン性能計測結果

- **対象**: `src/scholarrepo_finder/collector.py`、`src/scholarrepo_finder/pipeline.py`
- **目的**: GitHub Actions上のクロール処理の実測値をベースライン化し、性能改善の優先順位を判断する。
- **ステータス**: 初回観測結果
- **観測対象コミット**: `d84621b`（PR #9 マージ後の `main`）
- **実行環境**: GitHub Actions、Python 3.14.7、`uv run python -m scholarrepo_finder.pipeline`

## 1. 入出力

| 項目                                    |              実測値 |
| --------------------------------------- | ------------------: |
| 収集したリポジトリメタデータ数          |               932件 |
| 掲載閾値（Score >= 60.0）を通過した件数 |               251件 |
| スコア設定                              | `reusability-v1` v1 |

外部APIの検索結果、リポジトリ更新、応答時間は実行ごとに変動する。したがって本結果は単一実行のベースラインとして扱い、候補件数や掲載件数の小さな差だけで回帰と判断しない。

## 2. 所要時間

| 区間      |                所要時間 | 構成比 | 内容                                                   |
| --------- | ----------------------: | -----: | ------------------------------------------------------ |
| Step 1    | 1,343.7秒（22分23.7秒） |  88.5% | GitHub検索・README・ツリー・依存定義・所有者情報の収集 |
| Step 2    |    175.5秒（2分55.5秒） |  11.5% | PWC照合、特徴抽出、スコアリング                        |
| Step 3〜5 |               0.1秒未満 |   0.0% | 観測レポート、静的データ、Markdownの生成               |
| 合計      | 1,519.2秒（25分19.2秒） | 100.0% | パイプライン全体                                       |

Step 1は100件ごとに121.0〜164.7秒を要した。Step 2は100件ごとに10.3〜46.2秒であり、外部PWC照合の応答時間による変動がある。

## 3. 判断

性能改善の最優先対象は、全時間の約88.5%を占めるStep 1である。Step 2だけを改善しても全体への効果は限定的であり、Step 3〜5は対象外とする。

まずGitHub HTTPクライアントをパイプライン内で共有して接続を再利用する。次に、GitHub APIのレート制限・失敗時の扱いを計測したうえで、上限付き並列化または差分キャッシュを検討する。探索対象数や掲載閾値を減らす施策は、性能改善ではなく探索品質を変更するため、本観測を根拠としては採用しない。

## 4. 再計測条件

性能改善後は、同じスコア設定と既定のシード集合で再実行し、Step 1・Step 2・合計時間、収集件数、掲載件数を本結果と比較する。GitHub Actionsのランナーと外部APIの揺らぎを考慮し、1回の差ではなく複数回の傾向で判断する。

## 6. 次の改善案（未着手）

Step 1は953.3秒・932件で、1件あたり平均約1.02秒を要している。HTTPクライアント共有化は接続確立コストを削減したが、`fetch_repository_details` 内のAPI呼び出し（README・ファイルツリー・依存定義・所有者情報）は依然として逐次実行であり、待ち時間そのものはまだ残っている。優先度の高い順に次の案を検討する。

| 優先度 | 案                                                                                               | 効果                  | リスク・留意点                                                                                                                      |
| ------ | ------------------------------------------------------------------------------------------------ | --------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 高     | `fetch_repository_details` 内の独立したAPI呼び出し（README・ファイルツリー・所有者情報）の並列化 | Step1レイテンシの短縮 | 依存定義ファイル取得はファイルツリー結果に依存するため並列化対象外。GitHubのSecondary rate limit（同時実行数の急増）に注意が必要    |
| 中     | リポジトリ単位（932件）の上限付き並列化                                                          | 高（候補内で最大）    | レート制限・失敗時のバックオフ・出力順の決定性を先に設計する必要がある。観測強化（呼出数・status・`X-RateLimit-*`）を先行させるべき |
| 低     | `httpx.Client(http2=True)` の有効化                                                              | 不明（未検証）        | `httpx[http2]` の追加依存が必要。GitHub API側の対応状況次第で効果が変動するため実測での判断が前提                                   |

探索対象数や掲載閾値を減らす施策は、性能改善ではなく探索品質を変更するため、引き続き本観測を根拠とした改善案としては採用しない。

Step 1は大幅に短縮したが、掲載件数が250件から39件へ大きく減少した。この時点ではAPI呼び出しの成否を観測する仕組みがなく、ログにも403/429等のエラー記述は見られなかったため、GitHubのSecondary rate limit（同時実行数の急増によるブロック）への抵触が疑われたが、当時のログからは断定できなかった。4節・1節の方針（小さな差は回帰と判断しない）を踏まえても、211件という差は無視できる範囲を超えていたため、断定せず観測強化を先行させることにした。

### 7.3 判断

今回の実行では並列化によるレート制限抵触は検出されず、掲載件数もベースラインと一致した。これは「並列化コード自体に恒常的な欠陥がある」という仮説を支持しない結果である。一方で、PR #11時点の39件という結果を観測なしで遡って検証する手段はなく、外部要因（GitHub側の一時的な障害、ネットワークの揺らぎなど）による単発の異常値だった可能性が残る。断定はせず、原因不明のまま経過を見守る。

Step 1の所要時間は179.0秒〜953.3秒の範囲で大きく変動しており、並列化の効果よりも実行ごとの外部要因（GitHub Actionsランナー、GitHub API応答時間）の揺らぎが大きい可能性がある。4節の方針どおり、今後も複数回の実行結果を継続観測し、`rate_limit_*` カテゴリの出現頻度と掲載件数の変動を突き合わせて判断する。
